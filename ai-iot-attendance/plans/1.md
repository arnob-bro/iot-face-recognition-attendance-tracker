Here's the consolidated master prompt, combining student accounts, routine-based scheduling, manual sessions, and cancellation into one coherent build plan for your agent:

---

> I'm extending the AI-IoT Attendance System backend (FastAPI + Firestore, see repo README) with four connected features. Please implement them together since they interact: student accounts, routine-based auto session start/end, manual session start/end, and session cancellation — all with a shared collision-prevention strategy.
>
> ## 1. Student accounts (new `student` role)
>
> - Add a `password_hash` field to the `students` Firestore collection (bcrypt, matching `teachers.password_hash`).
> - When admin creates a student via `POST /api/v1/students/`, either require a password at creation or auto-generate a temporary one with a "must change on first login" flag — pick whichever fits the existing auth service patterns, and tell me which you chose.
> - Add a `POST /api/v1/students/login` endpoint (or extend `POST /api/v1/auth/login`) that checks the `students` collection and issues a JWT with `role: "student"` and `student_id` in the claims, matching the JWT structure used for `teacher`/`admin`/`device`.
> - Add `GET /api/v1/students/me` (parallel to `/api/v1/devices/me`) returning the logged-in student's own profile.
> - Update role-checking dependencies to recognize `student` as a valid role, scoped to self-access only.
> - Add a self-service password change endpoint, separate from admin-driven resets.
>
> ## 2. Course-wise attendance history for students
>
> - Allow a `student`-role token to call `GET /api/v1/students/{student_id}/attendance` and `GET /api/v1/reports/student/{student_id}` **only when `student_id` matches their own token claim**; reject any request for another student's ID.
> - Confirm/extend these to support per-course grouping (the `course_id` query param already exists on the attendance endpoint) so a student sees a breakdown per enrolled course: total classes, present/late/absent counts, and percentage.
> - Do not weaken existing `admin`/`teacher` access — they still see all students.
>
> ## 3. Class routines (schedule model, for auto-session logic)
>
> - New Firestore collection `class_routines`: `course_id`, `teacher_id`, `device_id`/`room`, `day_of_week`, `start_time`, `end_time`, `late_threshold_minutes`, `is_active`, `created_at`.
> - Add `/api/v1/routines` CRUD: admin-only for create/update/delete, admin+teacher for read.
> - On create/update, reject overlapping routines for the same `teacher_id` OR same `device_id`/room on the same `day_of_week`, with a clear error naming the conflict.
>
> ## 4. Automatic session start/end, driven by routines
>
> - Background scheduler (e.g. APScheduler) inside the FastAPI app lifecycle, checking routines against current time.
> - At `start_time`: auto-create an `attendance_sessions` doc the same way `POST /api/v1/attendance/sessions` does (same defaults, `device_id` from routine), but only if no session for that `course_id` is already `active` (reuse the existing per-course active-session guard).
> - At `end_time`: auto-end it the same way `PUT .../{id}` with `status: completed` does, including marking unmarked enrolled students absent.
> - Add a `source` field on `attendance_sessions`: `"manual"` or `"routine"`, so reports can distinguish them.
> - On server startup, reconcile: if a routine window should currently be "in session" but no matching active session exists, start it late and log it (covers restarts/downtime).
> - Skip auto-restarting a routine's slot on a day where a session for that course+routine+date already exists in any terminal state (`completed` or `cancelled`) — don't refill a cancelled slot same day.
>
> ## 5. Manual session start/end, coexisting with auto sessions
>
> - `POST /api/v1/attendance/sessions` and `PUT .../{id}` keep working exactly as now for teacher/admin-initiated sessions.
> - The existing "one active session per course" and "device tied to its assigned active session" rules apply identically whether the active session is `source: manual` or `source: routine` — a manual start is blocked the same way if a routine session is already active for that course/device, and vice versa.
> - Collision checks (course-level and device-level) must only count sessions with `status == "active"` — `completed`/`cancelled` sessions never block a new manual session.
>
> ## 6. Session cancellation (teacher/admin), freeing the room
>
> - Confirm/fix `PUT /api/v1/attendance/sessions/{session_id}` with `status: cancelled` so it:
>   - Sets `status: cancelled` and stamps a `cancelled_at` timestamp.
>   - Does **not** trigger absent-marking (that's only for `completed`).
>   - Immediately releases the device/room so it's free for a new manual session on a different course.
> - Authorization: `teacher` can cancel only their own course's sessions; `admin` can cancel any. Reject cancelling an already-`completed`/`cancelled` session.
> - Record `cancelled_by` (and optionally `cancel_reason`) for audit purposes.
> - The routine scheduler must skip re-processing a cancelled session at its scheduled auto-end, and must not auto-restart that same slot later that day (ties into the rule in step 4).
>
> ## 7. Collision rules to centralize and comment clearly in code
>
> - No two `active` sessions for the same `course_id`.
> - No two `active` sessions on the same `device_id` at the same time.
> - No two routines for the same `teacher_id` overlapping on the same day.
> - No two routines for the same `device_id`/room overlapping on the same day.
> - Cancelling or completing a session always frees its course/device slot for a new manual session.
>
> ## 8. Tests (add to `backend/tests/`)
>
> - Student login, self-only access enforcement (can't fetch another student's attendance), course-wise attendance retrieval.
> - Routine overlap rejection (teacher case and device case).
> - Auto-session creation at routine start time, auto-end with absent-marking, startup reconciliation after simulated downtime.
> - Manual session correctly blocked/allowed against an active routine session on the same course/device.
> - Teacher cancels own session (succeeds) vs. another teacher's session (rejected); admin cancels any (succeeds).
> - Cancelled session frees the device for an immediate new manual session on a different course.
> - Cancelled session does not mark absences; cancelled routine slot is not auto-restarted same day.
>

>

>
> Please flag any design decision you have to make where the README doesn't specify an existing pattern to follow (e.g., password-at-creation vs. auto-generated, exact field names for cancellation), rather than guessing silently.
